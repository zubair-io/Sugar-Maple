# Browser acceptance source ownership

Candidate for #108 at implementation source `4965fd85b9b556d016ec4b201b5e8c567dd71da3`, based on verified main `29c1b47`. The complete browser harness owns its checkout's ephemeral-port loopback server, observes only the child's reported address, passes that URL to every current-main fixture and checks liveness. Owned server/fixture groups are stopped and awaited on normal completion, fixture failure, startup failure and SIGINT/SIGTERM; bounded cleanup verifies no live group members remain. Every run records checkout, revision, dirty files, bound URL, successful fixtures and cleanup state. Standalone fixture targeting remains explicit through SUGAR_MAPLE_TEST_URL, with the documented conventional-port default.

Typecheck and all 32 current-main browser/consumer suites passed on the new runner. The source/cleanup report confirms the exact source and complete fixture list; no conventional-port server was reused. Current application semantics and browser assertion thresholds are unchanged.

A focused concurrent ownership test started two actual checkout editors: this branch, whose export schema lacks new copy fragments, and web-copy candidate `7601b04`, whose schema includes them. Both exposed their own expected schema on distinct owned ports, and an unrelated 4200 canary remained intact with zero probes. This proves focused source isolation; it is not a complete pair of concurrent full-suite runs. Full two-checkout suite validation and adaptation of pending metadata/web-copy fixtures remain outstanding before final delivery.

Real failure cases launch a leaking child then throw, interrupt an active fixture with SIGTERM, and start from a missing checkout. All reject, report cleanup, leave no owned leaked descendant and preserve the unprobed unrelated listener. The original mixed-server failures are retained in the metadata/web-copy integration evidence; none counts as a pass. Local fixture scripts/results do not claim portable CI failure-case automation. Existing supervisor process/output/RSS bounds are reused as harness limits; they are not application performance acceptance.

This remains an unpublished-review candidate: pending feature integration, final CI/independent review, merge and resulting-main verification are required. #21/#27 remain open for their complete workflows and release acceptance.
