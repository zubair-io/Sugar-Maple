The product decision

Useful today: a local workbench for an engineer or agent to compose static web/mobile screens, edit the same scene with a pointer, explore simple click-through flows and produce starting code. The atomic command path, stable IDs, layout inspection, component propagation and human/agent undo are meaningful working foundations.

Not yet ready to promise: a complete Sketch/XD replacement, a high-fidelity production design-system workbench, or reliable cross-platform handoff for arbitrary designs. Several failures are silent: a component detaches on paste, a variant looks wrong, a valid route appears absent, or compiled output changes the typography.

Recommended wedge, to validate: small product teams building web and Apple interfaces who want agents and humans to design with their own real components and produce verified code locally. The differentiator should be a shared, inspectable component contract and tested handoff. This is a product hypothesis; no customer interviews, market sizing or willingness-to-pay study were conducted.

Prioritize correctness and daily design capability before broad library execution or advanced animation. A screen that looks good once is less valuable than a screen that survives reuse, resize, export and reopening.

What I created using the actual Sugar Maple MCP

I connected an SDK client to the authenticated editor-owned server at 127.0.0.1:48480/mcp. The images below are native WKWebView captures of real editable nodes. They are not raster mockups pasted onto the canvas.

Authoring quality: the dashboard and mobile screens are credible visual concepts. Mixed HTML/SVG, local tokens, stacks and components work. Fine design requires too much absolute positioning and text approximating icons because typography, constraints, semantic controls and library discovery are shallow. The dashboard uses primitive containers for its table; it does not claim a production table component.

What held up: atomic creation, parent-cycle rejection, retry idempotency, same-document component structure propagation, text overrides, repeat titles, resolved comment threads and live pointer-to-MCP readback. Agent undo preserved a separate human drag; human undo and redo restored the expected geometry. Human/agent evidence.

What exposed limits: a fixed-child row overflows at 320 px because the model lacks wrapping/min-max decisions. Its fill width was correct at 458 px; an earlier harness expectation of 426 px was corrected. Likewise, the initial batch contained 117 nodes, not the harness’s expected 116. Those two were test mistakes, not product defects.

Compilation is not visual fidelity

The Angular export compiles under strict checking, Tailwind classes compile, and SwiftUI typechecks and renders. That is valuable evidence of syntax and compatibility, but does not establish visual parity. The offscreen SwiftUI fixture has its own appearance environment; the white placeholder appearance should be reproduced in a controlled light/dark consumer before assigning its exact cause. Missing control font modifiers and stack padding are independently visible in generated source. Consumer measurements.

P1 QA-01 · Detailed errors disappear at the native bridge

Reproduce: Call transaction.apply with a stale revision or wrong document; submit an invalid batch; export an unsupported SwiftUI layout.

Observed: Each returns “A JavaScript exception occurred”. The invalid edits are correctly rejected, but the client cannot distinguish why.

Needed: Stable error code, readable cause, current document/revision and recoverable action; preserve unsupported-feature details.

Product impact: Agents cannot repair requests reliably; humans cannot diagnose export limitations.

Confidence: Live MCP + source · Existing work: #5 #20 #27 · deep-qa-calls.json · assets-calls.json

Reproduce: Call code.export with target:"png", which is outside the advertised enum.

Observed: Successful HTML response instead of validation failure.

Needed: Reject invalid tool inputs before dispatch; export target and response MIME must agree.

Product impact: A successful protocol response can produce the wrong artifact.

Confidence: Live MCP · Existing work: #20 #27 · recheck-calls.json

Investigations, not established root causes

The initial editor showed “Saved to .syrup bundle” alongside “The file ‘document.json’ couldn’t be opened.” A picker attempt later reproduced that alert after an uncertain selection. The native open panel currently accepts arbitrary files/directories and presents .syrup as a folder. Improve package selection and error context, then reproduce save → close → reopen explicitly. This observation is not proof of lost data or failure to read the correctly selected package. The saved QA package exactly matches the live scene.

Native color wells appeared black even when accessibility values contained the correct RGB values. Investigate WKWebView/CSS rendering and compare Chrome; do not yet classify it as a document token corruption bug. Initial native screenshot.

Important missing semantics

The model has generic input/button nodes, not an implemented form contract. A password-looking input shows plain text in preview and exports as a text field without an associated accessible label. Calling a visual variant “Disabled” does not disable its control. Treat typed controls, labels, focus, validation and state binding as explicit features; names alone should not infer behavior.

What Sketch and Adobe XD reveal

Sketch is an active benchmark: its built-in local MCP can read and modify documents, discover assets/libraries, inspect overrides and capture layers. Its run_code exposes Sketch’s JavaScript API. Sugar Maple cannot rely on local MCP alone as a moat. A validated command contract, portable scene semantics and dependable multi-target consumers are a more specific potential advantage. Sketch MCP documentation.

Adobe XD is a workflow benchmark: Adobe describes it as in maintenance mode. Use its mature design/prototype interactions to understand user expectations, rather than model a roadmap against an actively evolving XD release. Adobe XD support status.

Additional gaps in the end-to-end product

Tokens: current document bindings cover opaque hex colors. Typography, spacing, radii, shadows, aliases and theme modes need explicit types and resolution rules. UI color DTCG import/export exists, but there is no corresponding import/discovery tool in the 13-tool MCP inventory. Design tokens must remain document data, independent of the host theme.

Agent ergonomics: there is no scoped scene query, open-document list/switch tool, component catalog search, asset import tool or node-cropped capture. Mutation is revision/document scoped, but read/export/selection tools are less consistently targeted. Full-document reads amplify context and serialization costs. Capture returns the editor shell, not a clean artboard asset; its throttling is not explained by the input schema.

Workspace and review: file tabs, folders, save state and local comments exist. Next prove recent-file/recovery behavior, library linkage status and a portable review package. Settings, panel ergonomics, keyboard access and screen-reader operation need a dedicated native acceptance pass; they were not comprehensively audited here.

Content and visuals: bundled authored font selection, icon/assets discovery, image crop/fill and realistic multi-field repeated data matter for daily UI work. Add explicit unsupported-feature feedback rather than approximating these capabilities with names or decorative primitives.

The gap is more than feature count: established tools let designers express intent quickly, reuse it safely and inspect results. Sugar Maple should earn that reliability for a focused set of workflows. Competitor claims above come from current official documentation, not hands-on testing of their desktop apps during this review.

The proposed user journey

  1. Choose a local manifest or recognized package and inspect components, versions, dependencies and license/provenance.
  2. Preview declared examples: default, disabled, loading, validation error and localized content.
  3. Insert a component; edit typed props and slots, bind document tokens, keep the source symbol visible.
  4. In Developer mode, copy the exact import, component call, dependencies and required assets; compile in a real consumer.
  5. Review a library update as a diff: changed props, defaults, visuals, removed symbols and affected instances. Keep the previous version available.
  6. When the library is absent, show a preserved portable fallback and an explicit linkage status. Do not silently detach.

Storybook portable stories can reuse composed story examples outside Storybook; they are a possible fixture input, not a guaranteed reverse-design importer. Custom Elements Manifest gives useful declarative API metadata. SwiftSyntax provides source parsing/inspection; it does not supply evaluated SwiftUI semantics. These support the proposal but do not establish that arbitrary libraries can be imported automatically. Storybook portable stories; Custom Elements Manifest analyzer; SwiftSyntax.

A minimal proposed contract

{
  "component": "acme.button", "version": "1.2.0",
  "props": { "label": "string", "tone": ["primary", "danger"], "disabled": "boolean" },
  "slots": ["leadingIcon"],
  "exports": { "angular": "AcmeButton", "swiftui": "AcmeButton" },
  "tokens": { "background": "color.brand" },
  "fallback": "portable-scene-reference",
  "source": "pinned-package-or-local-manifest"
}

This is an illustrative product contract, not the current schema and not a complete wire specification. Use exact per-framework prop types and mappings in implementation. Keep package/version/provenance in document data; host Maple chrome must remain separate. Do not scrape a rendered DOM to reconstruct authored meaning.

Concept screens built in Sugar Maple

Decision gate: a developer supplies one Angular component and its SwiftUI counterpart. A designer inserts, changes props/tokens/states, resizes, copies code and reopens offline. Both real consumers compile and match documented tolerances. If this takes hidden manual source repair or loses identity, do not broaden to more frameworks yet.

Scope to defer

Voice prototypes, multiplayer/coediting, a mobile companion, general plugin execution, broad source-to-scene conversion and advanced vector illustration should follow proven everyday design and handoff. Basic typography, reliable component reuse, common prototype flows and measured performance are not optional polish for the proposed product.

How to validate the product hypothesis

Recruit a small cohort of web/Apple product teams using an existing component library. Observe three tasks: reproduce an existing screen from their components; change the system and inspect affected instances; hand off and compile a responsive screen. Include a designer working without an agent and an engineer receiving the file. Ask what forced them to leave the tool and what they repaired manually.

Track time to first useful screen, task completion without workarounds, export compile rate, fidelity failures, preserved component linkage, recovery success and successful agent correction after typed errors. Establish a baseline before setting numerical targets. Prioritize demonstrated task blockers over a speculative parity checklist or invented RICE scores.

Performance evidence

On a MacBook Pro with Apple M5 Max and 128 GB RAM, I added 1,000 mixed nodes plus an artboard to the QA document, producing 1,141 total scene nodes. Twenty sequential read-full-document + edit MCP round trips had median 201.34 ms, p95 208.19 ms and max 214.20 ms. Layout inspection took 53.44 ms. All 1,001 page nodes were mounted, including content clipped below the artboard. All temporary edits were undone and the prior scene was restored exactly. Raw timing samples.

These are transport/serialization round trips, not frame times or local commit timings. They do not prove a 60 fps or an 8 ms budget. Next measurements should separate command validation, store update, layout/paint, MCP serialization and persistence on defined lower-end hardware. Scoped reads and subtree invalidation are likely valuable; full-document cloning/validation and repeated child filtering need profiling before an optimization commitment.

Coverage not completed
